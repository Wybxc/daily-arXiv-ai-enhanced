### [1] [te-comp: A Complete MLIR Compiler Generating Self-Contained C Inference Engines for MCUs](https://arxiv.org/abs/2611.03710)
*Van Chan Ngo*

Main category: cs.PL

TL;DR: te-comp is the first complete MLIR-based compiler that takes a .tflite or .safetensors model and emits self-contained, dependency-free C source (kernels, weights, memory layout, RTOS layer). It beats MCUNet TinyEngine on 10 CNN benchmarks and deploys an 8.3M-param GPT-Neo on a Cortex-M7.


<details>
  <summary>Details</summary>
Motivation: 在MCU上部署深度学习需将权重与运行时激活压缩到数十至数百KB的SRAM/Flash中。现有方案要么使用带预写kernel库的解释器，要么用Python代码生成器配合手写C kernel，带来调度开销与框架依赖，且均无法产出针对特定模型自包含、无依赖的C代码。

Method: 提出te-comp，一个完整的基于MLIR的编译器：输入标准.tflite或.safetensors模型，输出部署所需全部C源文件，包括推理引擎（kernel、权重数组、内存布局）与RTOS集成层，实现零运行时依赖。针对Transformer，采用Q4_0权重量化、有状态int4 KV cache与词表剪枝。

Result: 在10个MCUNet CNN基准上，相比TinyEngine减少38%SRAM（最多5.9倍）与15%Flash，且生成完整C代码而非链接预写kernel库。编译8.3M参数GPT-Neo并在单核160MHz Cortex-M7上部署：固件占用249KB/512KB SRAM、3.62MB/4MB Flash，约1 token/s交互式文本生成。

Conclusion: te-comp证明了基于MLIR的端到端编译可生成无依赖、模型特化的C代码，在CNN上优于现有MCU推理引擎，并首次在单核MCU上实现Transformer生成式推理，填补现有MCU推理框架的能力空白。

Abstract: Deploying deep learning on microcontrollers (MCUs) requires fitting both the model weights and runtime activations within tens to hundreds of kilobytes of SRAM and Flash. Existing approaches either use an interpreter with a pre-written kernel library or combine a Python code generator with hand-written C kernels. This incurs dispatch overhead and requires framework dependencies. None produces self-contained, dependency-free C code specialized to a given model.
  In this paper, we present te-comp, the first complete MLIR-based compiler that takes a standard model in .tflite or .safetensors format and emits all C source files needed for deployment: the inference engine (kernels, weight arrays, memory layout) and the RTOS integration layer with zero runtime dependencies.
  On 10 MCUNet CNN benchmarks, te-comp outperforms MCUNet TinyEngine by using 38% less SRAM (up to 5.9$\times$) and 15% less Flash, while generating complete C code rather than linking a pre-written kernel library. To demonstrate, we use te-comp to compile an 8.3M-parameter GPT-Neo transformer (TinyStories-v2) and deploy it on a single-core Cortex-M7 at 160MHz. The full firmware uses 249KB of 512KB SRAM and 3.62MB of 4MB Flash and achieves approximately 1 token/s interactive text generation via Q4_0 weight quantization, a stateful int4 KV cache, and vocabulary pruning -- a capability no existing MCU inference framework supports.

### [2] [Silent Degradation during Auto-Vectorization of bf16/fp16 on RISC-V Under LLVM](https://arxiv.org/abs/2611.03917)
*Vaishnavi Kouru,Robert Chun*

Main category: cs.PL

TL;DR: 在通用基线目标 -march=rv64gcv 下，LLVM 的 RISC-V 自动向量化对 int8/fp32 处理良好，但对 bf16/fp16 退化为大量标量回退代码；启用 zvfbfmin/zvfbfwma、zvfhmin 后，bf16 与 fp16 的动态指令数分别降低至基线版本的 1/17.0 与 1/75.9，而编译器诊断无法区分"加 flag 即可解决"与"固有转换开销"。


<details>
  <summary>Details</summary>
Motivation: 低精度类型（int8、bfloat16、fp16）在 AI 推理中广泛用于降低访存带宽，RISC-V RVV 是自动向量化的天然目标。但现有工作未系统检验 LLVM RISC-V 自动向量化器对不同窄类型是否同等有效；若基线目标下窄类型无法正常向量化，编译产物会静默劣化，而编译器诊断的信息量是否足以指导用户修复尚不清楚。

Method: 构造面向 fp32、int8、bf16、fp16 的同构乘累加（MAC）循环微基准，在统一基线目标 -march=rv64gcv 下用 LLVM 编译；结合汇编级指令分析、LLVM optimization remarks 直接检查，以及在 QEMU user-mode 仿真下采集动态指令数，并对比启用 zvfbfmin/zvfbfwma 与 zvfhmin 扩展后的版本。

Result: 基线目标下 int8 与 fp32 可干净向量化；bf16 与 fp16 退化为逐级加重的标量回退代码，fp16 甚至回退为逐元素软件转换函数调用。QEMU 用户态仿真中，基线 bf16、fp16 内核的动态指令数分别为启用扩展版本的 17.0× 与 75.9×。编译器诊断能报告该退化，但措辞上未区分可由编译选项完全解决的局限与固有转换开销。

Conclusion: LLVM RISC-V 自动向量化器对窄浮点类型的支持显著不均衡，基线目标下 bf16/fp16 存在严重性能缺口，需显式启用 zvfbfmin/zvfbfwma、zvfhmin 才能消除；同时现有诊断信息缺乏可操作性，无法直接指向修复手段。研究建议改进诊断措辞以区分可配置性局限与架构固有开销，结论由汇编分析、optimization remarks 与动态指令计数三重证据支撑。

Abstract: Low-precision numeric types such as 8-bit integers, bfloat16, and half-precision floating point (fp16) are often used in AI inference workloads to reduce memory bandwidth, and RISC-V's openly specified Vector extension (RVV) is a natural target for compiling such workloads with auto-vectorization. This paper examines whether LLVM's RISC-V auto-vectorizer handles these narrow types equally well, using a multiply-accumulate loop written for fp32, int8, bf16, and fp16. Under a common baseline target (-march=rv64gcv), int8 and fp32 vectorize cleanly, while bf16 and fp16 degrade to increasingly scalar-heavy fallback code, with fp16 falling back to per-element software conversion calls, unless additional target-feature extensions (zvfbfmin/zvfbfwma, zvfhmin) are enabled. Under QEMU user-mode emulation, the baseline bf16 and fp16 kernels execute $17.0\times$ and $75.9\times$ as many dynamic instructions as their extension-enabled counterparts. Compiler diagnostics do report this degradation, but do not distinguish, in their wording, between a limitation that a compiler flag resolves entirely and one reflecting an inherent conversion cost, leaving no direct signal toward the fix. These results are supported by assembly-level instruction analysis, by direct inspection of LLVM's optimization remarks, and by dynamic instruction counts collected under emulation.

### [3] [Handling JAX](https://arxiv.org/abs/2611.03918)
*Oghenevwogaga Ebresafe,Daniel Zheng,Gordon Plotkin,Ningning Xie*

Main category: cs.PL

TL;DR: 本文提出将 effect handlers 静态消除并编译到受限的硬件加速器目标语言的翻译技术，证明了类型安全与语义保持，并在 Lean 4 中机械化验证，最后实现为 JAX 库并用于实际案例。


<details>
  <summary>Details</summary>
Motivation: 面向硬件加速器的语言通常只暴露受限的一阶核心（无递归、无一等函数），使程序员缺乏表达计算效应（computational effects）的原则性手段。作者希望在不扩展目标语言能力的前提下，为这类受限目标提供 effect handlers 的表达能力。

Method: 提出一种新颖的静态消除 effect handler 的翻译（compilation technique）；针对结构化控制流下 continuation 无法静态构造的挑战给出处理方案；用 Lean 4 证明辅助器对演算与全部结果进行完整机械化验证；并以 JAX（Python 面向加速器编程的 DSL）库形式实现该设计。

Result: 证明该翻译保持类型（typing preservation）与语义（semantics preservation）；在 Lean 4 中完整机械化；JAX 库实现通过实际案例研究展示了其表达力。

Conclusion: effect handlers 可以在编译期被静态消除并映射到受限的一阶加速器目标，且该转换在类型与语义上可靠；同时能与结构化控制流兼容，具备工程可实现性与实用表达力。

Abstract: Languages that target hardware accelerators typically expose a restricted, first-order core without recursion or first-class functions, leaving programmers without a principled way to express computational effects. This paper presents a technique for compiling effect handlers to such a constrained target. We introduce a novel translation that statically eliminates effect handlers, and prove that it preserves both typing and semantics. Moreover, we address the challenges of integrating effect handlers with structured control flow, where continuations cannot be constructed statically. The calculus and all our results are fully mechanized in the Lean 4 proof assistant. Finally, we implement our design as a library for JAX, a Python domain-specific language for accelerator programming, and demonstrate its expressiveness through practical case studies.

</details>


### [4] [Proving the Wrong Program: Miscompilations as a Threat to zkVM Guarantees](https://arxiv.org/abs/2611.04701)
*Hui Xuan Tan,Stefanos Chaliasos,Alastair F. Donaldson*

Main category: cs.PL

TL;DR: 本文首次实证研究"编译器错误编译（miscompilation）"对 zkVM 保证的威胁：在 SP1 与 Jolt 上，48/46 个已知 rustc/LLVM bug 可使 guest 提交错误输出；攻击者可故意在 guest 代码中引入看似正常的优化补丁来触发这些 bug，且无法通过审查或形式化验证源码发现。


<details>
  <summary>Details</summary>
Motivation: zkVM 证明覆盖的是编译后的 RISC-V 二进制，而非开发者源码，因此编译器错误编译会让正确源码产生"有效但错误"的计算证明。该威胁此前缺乏系统性实证，作者希望量化：已知编译器 bug 有多少能在生产级 zkVM 上复现、偶然触发的概率多大、以及对抗性场景下的可利用性。

Method: （1）构建含 88 个有 Rust 复现用例的已知 rustc 与 LLVM 错误编译数据集，并用 LLM agent 为 124 个仅以 LLVM IR 报告的 bug 中的 60 个恢复 Rust 触发用例；（2）在 SP1 与 Jolt 上逐一实测复现；（3）对 10 个流行 SP1 项目中 13 个 guest 程序，比较 buggy 与修复后编译器生成二进制的差异及在测试输入上的行为；（4）模拟攻击者：用 LLM agent 以约 40 美元/项目的成本，为 guest 代码生成"看似普通优化、保持源码语义、但暴露已知 bug"的补丁，并在 20 个项目上验证。

Result: 复现方面：88 个 bug 中 48 个使 SP1 guest 提交错误输出，46 个在 Jolt 上成立，其中 15 个 rustc bug 两者共同命中；未复现者多因目标 ISA 缺失相应指令扩展而根本执行不到出错路径。偶然触发方面：552 个可构建的 guest–bug 组合中 447 个二进制逐字节相同，其余 105 个代码相同或在所有测试输入上行为一致，说明现有程序几乎不会意外中招。对抗场景方面：366 个项目–bug 组合中 12 个（覆盖 20 个项目中的 11 个）被注入成功，4 例产生错误输出（含某以太坊客户端拒绝合法区块），8 例在合法输入上崩溃/失败。

Conclusion: 错误编译构成真实且可被蓄意利用的 zkVM 安全威胁：补丁与源码均正确，审查与形式化验证无法拦截。zkVM 项目应将编译器纳入可信基（TCB），并跟踪所用工具链的已知 bug。

Abstract: A zero-knowledge virtual machine (zkVM) lets an untrusted prover convince a verifier that a program, typically Rust compiled to RISC-V, ran correctly. The proof covers the compiled binary, so a miscompilation can make a correct zkVM produce a valid proof of a computation that differs from the developer's source. We present the first empirical study of miscompilation as a threat to zkVM guarantees, on the production zkVMs SP1 and Jolt. We assemble 88 known rustc and LLVM miscompilations with Rust reproducers, using an LLM agent to recover Rust triggers for 60 of 124 LLVM bugs reported only as LLVM IR. Many of the bugs carry over to zkVMs: 48 of the 88 make a guest commit a wrong output on SP1 and 46 on Jolt, including the same 15 rustc bugs on both. Most bugs that do not reproduce never reach the faulty code on the zkVM's target, e.g. because they need an instruction-set extension. Existing guest programs are rarely affected by accident. Across 13 guests of 10 popular SP1 projects, the buggy and the fixed compiler produce byte-identical binaries in 447 of the 552 guest-bug pairs that build, and the other 105 have the same code or agree on every input we ran. An attacker who contributes code to a guest, however, can trigger these bugs on purpose. For about $40 per project, an LLM agent found patches that look like ordinary optimisations, preserve the behaviour of the guest's source, and expose a known bug in 12 of 366 project-bug pairs, across 11 of 20 projects. In four cases the guest commits a wrong output, including an Ethereum client that rejects a valid block, and in the other eight it fails on a valid input. Reviewing or formally verifying the zkVM or the guest's source cannot catch such a patch, because both are correct. zkVM projects should treat their compiler as part of their trusted base and track the known bugs of their toolchain.

### [6] [Linking as Evaluation: Correct Separate Compilation via First-Class Environments](https://arxiv.org/abs/2611.04993)
*Jam Kabeer Ali Khan,Jinhao Tan,Bruno C. d. S. Oliveira*

Main category: cs.PL

TL;DR: 本文提出 $λ_{\mathsf{SCE}}$：一个将链接、模块与环境均作为一等公民的简单类型演算，通过类型导向的翻译把 link 算子编译为一等环境核心演算的普通项，使“链接即求值”，从而在构造上保证编译与链接可交换，进而由静态/动态链接的语义保持直接推出分离编译正确性；理论在 Lean 4 中机械化，并实现到 WebAssembly 的编译器。


<details>
  <summary>Details</summary>
Motivation: 分离编译的语义正确性（链接后程序与合并源码后程序行为一致）比类型安全性更难证明，因为需要对链接过程本身给出形式化刻画；作者希望让该性质从语言设计中自然涌现，而非事后单独证明。

Method: 设计简单类型演算 $λ_{\mathsf{SCE}}$，其中链接、模块、环境为一等公民；程序员通过 link 算子控制模块链接，类型导向的 elaboration 将其翻译为一等环境核心演算的普通项，由核心演算既有求值规则完成链接（linking as evaluation）；证明独立编译模块的链接结果与对源码链接再 elaboration 的结果相同（编译与链接可交换）；在 Lean 4 中机械化全部元理论，并用 OCaml 实现到 WebAssembly 的编译器。

Result: 建立了链接即求值的语义框架，构造性地得到编译与链接的可交换性；由此静态链接与动态链接的语义保持定理直接蕴含分离编译正确性；全部元理论在 Lean 4 中机器验证，并具备可运行的 WebAssembly 编译实现。

Conclusion: 将链接内化为求值、把模块与环境提升为一等对象，可使分离编译正确性成为语义保持的推论，避免了为链接单独建立形式化模型与证明的负担；该思路可机械化验证并落地为实际编译器。

Abstract: Separate compilation is central to modular software: components are compiled independently and linked into an executable. Separate compilation is correct when a linked program behaves like the program formed by merging its sources. This property is less routine to prove than type soundness because it requires a formal account of linking.
  We present $λ_{\mathsf{SCE}}$, a simply typed calculus in which linking, modules, and environments are all first-class. Programmers control module linking through a link operator, which a type-directed elaboration translates into ordinary terms of a core calculus of first-class environments. The core calculus's existing evaluation rules then perform the linking: linking as evaluation. Linking independently compiled modules yields the same core term as elaborating their source link. Therefore, compilation and linking commute by construction. As a result, separate compilation correctness follows directly from the semantics preservation for both static and dynamic linking. All meta-theory is mechanized in Lean 4, and we implement a compiler to WebAssembly in OCaml.

</details>
