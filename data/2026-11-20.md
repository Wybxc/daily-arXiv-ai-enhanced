### [1] [When Is Program Structure Required? Certificate-Grounded Calibration of Program-Induction Difficulty](https://arxiv.org/abs/2611.24975)
*Wenzhang Du*

Main category: cs.PL

TL;DR: 论文提出“证书接地校准”（certificate-grounded calibration），在受限字符串替换语言中构造最小解长度分别为1和2的匹配任务，实验证明在两规则生成器上，模型在“已展示任务”上完成率显著下降，而在未展示的witness对上成功率反而升高。


<details>
  <summary>Details</summary>
Motivation: 程序归纳基准只有在示例确实要求目标结构时才有意义；但两规则生成器可产生单规则即可解释的示例，导致基准区分度失效、任务难度被高估或低估。

Method: 构造最小解长度分别为1和2的匹配任务对：通过完全的单规则枚举排除单规则解释，并用可执行的两规则witness证书在模型推理前认证难度分离。评估120个参考族（每族3–6个共享示例），使用1,440条新模型轨迹与480条已保存轨迹，模型为Qwen3-8B与Olmo-3-7B-Think。

Result: 在认证分离任务上，已展示任务完成率下降23.53–45.83个百分点；而在完全未展示的witness对上成功率反而提升8.40–13.45个百分点。witness增益伴随在均匀采样字符串上更低的一致性，以及激活两条参考规则的输入上仅1.93–5.78%的一致性。重新认证还显示，单个未改动示例即可排除捷径并决定是否需要两条规则。

Conclusion: 示例所提供的证据会同时塑造所需解的结构与模型实际生成的程序；该构造为在可验证任务要求下比较程序搜索、最终答案交付及新输入行为提供了可执行测试平台。

Abstract: A program-induction benchmark is informative when its examples require the structure it aims to test. Yet a two-rule generator can produce demonstrations that a single rule also explains. We introduce certificate-grounded calibration, which constructs matched tasks with minimum solution lengths of one and two in a bounded string-replacement language. Complete one-rule enumeration and an executable two-rule witness certify the change before model inference. We evaluate 120 reference families with three to six shared examples, using 1,440 new model trajectories and 480 saved trajectories. Across Qwen3-8B and Olmo-3-7B-Think, displayed-task completion is 23.53-45.83 percentage points lower on certified separation tasks, while success on a wholly unshown witness pair is 8.40-13.45 points higher. These witness gains accompany lower agreement on uniformly sampled strings and 1.93-5.78% agreement on inputs that activate both reference rules. Recertification also reveals that a single unchanged example can exclude a shortcut and determine whether two rules are required. Together, these results show how the evidence supplied by examples shapes both the required solution and the programs models produce. The construction provides an executable testbed for comparing program search, final-answer delivery, and behavior on new inputs under verified task requirements.

### [2] [Mode Inference for Substructural Adjoint Types](https://arxiv.org/abs/2611.24984)
*Sophia Roshal,Frank Pfenning*

Main category: cs.PL

TL;DR: 本文提出面向伴随类型（adjoint types）的模式推断算法，产出主模式（principal modes），以简单约束语言概括函数所有可能的子结构模式。


<details>
  <summary>Details</summary>
Motivation: Jang et al. (2024) 的伴随类型可在类型系统中混合子结构模式（线性、仿射、严格、无限制等），但其算法类型系统在模式上是单态的，程序员须预先枚举大量模式组合，并可能为适配每种组合而复制代码。

Method: 定义带伴随类型程序的模式推断算法，用简单的约束语言生成主模式，从而对所有可能的子结构模式进行统一概括。

Result: 解除程序员预先分析代码子结构性质的负担，并使单个函数定义可涵盖其在多种模式下的所有实例；证明了该系统相对于 Jang et al. 单态版本的一个温和限制是可靠且完备的。

Conclusion: 模式推断使伴随类型系统由单态走向多态化使用，在保持原有证明论与计算性质的前提下，获得可靠性、完备性与主模式性。

Abstract: Adjoint types [Jang et al. 2024] provide a method of mixing substructural modes (for example, linear, affine, strict, or unrestricted) in a type system while preserving the proof-theoretic and computational properties of each mode. Uses of such a system include performing compiler optimizations or providing safety guarantees on parts of a program whose modes support them, while not restricting the programmer's ability to write other code as they usually do. However, Jang et al.'s algorithmic type system is monomorphic in the modes, requiring the programmer to anticipate a potentially large number of combinations of modes, and possibly copy code to conform to each of them.
  In this paper we define a mode inference algorithm for programs with adjoint types that produces principal modes, summarizing all possible substructural modes of a function in a simple constraint language. This removes the burden from the programmer to a priori analyze the substructural properties of their code, and, furthermore, allows a single function definition to subsume all its instances at different modes. We show that our system is sound and complete with respect to a mild restriction of Jang et al.'s monomorphic version.

### [3] [Tenon: A Unified Programming Framework for Retargetable PIM Compilation](https://arxiv.org/abs/2611.25636)
*Niansong Zhang,Shiran Guo,Zhiru Zhang*

Main category: cs.PL

TL;DR: Tenon是面向PIM（存内计算）的可重定向统一编程框架，将编译目标抽象为计算/存储单元的嵌套网格，并推广F2线性布局代数实现最小数据搬移的自动布局，在6个PIM后端上匹配或超越厂商与专家基线。


<details>
  <summary>Details</summary>
Motivation: PIM正成为异构系统处理访存密集型负载的构件，商业原型涵盖近bank SIMD引擎、bank级GDDR加速器、可编程DRAM核与SRAM内位级处理器；但各厂商编程栈碎片化，缺乏共享抽象与编译器，设备模型从指令序列到类C语言各异。同时计算-存储紧耦合使数据布局成为一阶优化问题，现有PIM编译器缺乏统一的布局表示与优化手段。

Method: 核心观察是PIM编译目标可建模为由合法数据传输路径连接的计算与存储单元嵌套网格。Tenon解耦负载、编译目标与代价模型，负载只表达一次即可通过统一框架编译；将GPU编译器中的F2线性布局代数推广到此类计算/存储网格，把逻辑工作与数据映射到物理单元，并在给定负载与目标规格下自动构造最小数据搬移布局。

Result: 在6个PIM后端上评估（5个商业后端与学术HBM-based架构AttAcc）。商业后端上匹配或优于厂商、专家及编译器基线，几何平均加速最高1.20×，单点最高3.65×。在AttAcc上端到端GPT-13B解码，三种batch-4配置下均比SOTA PIM编译器DCC快1.2–1.3%。

Conclusion: 结果表明Tenon在不同PIM目标族之间具备性能可移植性，统一抽象与自动最小搬移布局能有效应对PIM编程栈碎片化与布局优化难题。

Abstract: Processing-in-memory (PIM) is emerging as a building block of heterogeneous systems for memory-bound workloads, and commercial prototypes now span near-bank SIMD engines, bank-level GDDR accelerators, programmable DRAM cores, and bit-level in-SRAM processors. Their programming stacks are fragmented: no abstraction or compiler is shared across vendors, and per-device models range from instruction sequences to C-like languages. Data layout further complicates the problem: tight compute-memory integration makes data layout a first-order optimization, yet existing PIM compilers lack a unified way to represent and optimize it. A key observation is that PIM compilation targets can be modeled as nested grids of compute and storage units connected by legal data-transfer paths. We present Tenon, a unified programming framework for retargetable PIM compilation. It decouples workload, compilation target, and cost specifications, so a workload is expressed once and compiled through a unified programming framework. Tenon generalizes the $\mathbb{F}_2$ linear layout algebra from GPU compilers to map logical work and data onto these compute and storage grids. It automatically constructs a minimum-movement data layout given a workload and a target specification. We evaluate Tenon on six PIM backends: five commercial backends and AttAcc, a state-of-the-art academic HBM-based PIM architecture. Across the commercial backends, it matches or outperforms vendor, expert, and compiler baselines, with geometric-mean speedups of up to $1.20\times$ and individual speedups up to $3.65\times$. For end-to-end GPT-13B decoding on AttAcc, Tenon-compiled workloads run $1.2$--$1.3\%$ faster than those compiled by DCC, a state-of-the-art PIM compiler, across all three batch-4 configurations. Together, these results demonstrate Tenon's performance portability across diverse PIM target families.

</details>


### [4] [Sightline: Calibrated Data-Flow Summaries for LLM-Integrated Applications](https://arxiv.org/abs/2611.26221)
*Zihao Xu,Yuekang Li,Ruitao Feng,Haifeng Shen*

Main category: cs.PL

TL;DR: 该论文提出Sightline，通过注意力读写关系为LLM调用生成数据流摘要，无需第二模型标注即可在保证漏检率上界的前提下裁剪虚假流。


<details>
  <summary>Details</summary>
Motivation: 程序越来越常调用LLM并用程序值填充提示占位符，产生了跨自然语言与编程语言（NL/PL）边界的数据流。要追踪数据，需要知道输出使用了哪些占位符，但模型行为没有代码可描述。现有分析要么把每个输入都污染到每个输出（产生大量虚假流），要么再调用一个模型为每次调用打标签（代价高昂）。

Method: 作者在Lean 4中形式化并证明：一阶意义下，占位符只能通过读取它的注意力流到 transformer 输出（不读取则不流动），且微弱的读取或敏感度不能用来证明"不流动"；同时指出既有方法的log概率梯度与Fisher信号在置信输出上会消失、单跨度删除在重复内容上失效。Sightline在一次前向传播中读取记录下来的调用，用标签学习哪些"读取"是"使用"，并将裁剪阈值校准，使得在与校准分布可交换的部署条件下，平均每个调用点漏检的真实流不超过选定比例α。

Result: 在2,103个未见仓库族和四个模型上，Sightline相对七个最接近的基线方法和一个隐状态探针都是最准确的摘要。在α=1%校准下，漏检约1%的真实流，裁剪43.9–65.6%的虚假流，是最佳基线的1.6–2.6倍；在另一数据集上校准时仍达43.8–60.1%。通过开放代理模型，它读取被视为闭源的模型时准确度几乎等同于模型读取自身，且无需其标签。在LLM智能体的信息流控制中，它去除了不流动输入上约一半的标签。

Conclusion: Sightline将"是否流动"归结为可证明的注意力读取关系，并用带覆盖率保证的校准替代昂贵的逐调用标注，在准确度、虚假流裁剪和跨模型/跨数据集迁移上均优于现有方法，可直接用于LLM集成应用与智能体的信息流控制。

Abstract: Programs increasingly call large language models (LLMs), filling prompt placeholders with program values and consuming the output. Such a call crosses the boundary between natural language and programming language (NL/PL). To follow data across it, an analysis needs a data-flow summary of which placeholders the output uses, but no code describes what the model does. Analyses of these LLM-integrated applications therefore taint every output with every input, creating spurious flows, or ask a second model to label each call, which is costly. We prove, and mechanize in Lean 4, that a placeholder flows to the output of a transformer, to first order, only through the attention that reads it (no reading, no flow), and that a faint reading or sensitivity cannot certify that a placeholder does not flow. Unlike reading, the log-probability gradients and Fisher signals of existing methods vanish on confident outputs, and single-span removal fails on duplicated content. Our tool, Sightline, reads a recorded call in one forward pass, learns from labels which reads are uses, and calibrates the pruning to miss at most a chosen fraction $α$ of true flows, on average over call sites, when deployment is exchangeable with calibration. On 2,103 unseen repository families and four models, Sightline is the most accurate summary against the seven closest methods and a hidden-state probe. Calibrated at $α$ = 1%, it misses about 1% of true flows and prunes 43.9-65.6% of spurious flows, 1.6 to 2.6 times as many as the best baseline, and still 43.8-60.1% when calibrated on another collection. Through an open surrogate, it reads models treated as closed about as accurately as they read themselves, without their labels. In the information-flow control of an LLM agent, it removes about half of the labels from inputs that do not flow.

</details>


### [5] [You Have Mail: Set-Theoretic Types for Actors](https://arxiv.org/abs/2611.26563)
*Giuseppe Castagna,Luca Padovani,Daniele Varacca,Amine Nasri*

Main category: cs.PL

TL;DR: 本文为 Elixir 的 actor 进程提出一个静态类型系统：进程被类型化为 $\mathtt{pid}(t)$，其中 $t$ 是其邮箱接口类型；发送按接收方接口检查，接收依赖执行进程自身接口。系统通过为每个函数推断其可用邮箱类型的上下界，解决了邮箱隐式性与高阶消息传递（含 $\mathtt{self()}$ 与 receive）难以类型化的难题，并证明了可靠性。


<details>
  <summary>Details</summary>
Motivation: Elixir 是基于 actor 模型的动态语言，其现有静态类型系统仅覆盖函数式核心，进程与消息传递（邮箱）缺乏类型保障。核心难点在于邮箱是隐式的：随消息传递的函数可能在任意进程中执行，其中的 $\mathtt{self()}$ 与 receive 指令所作用的邮箱在函数书写处无法确定，导致高阶消息传递难以类型化。

Method: 1) 以 $\mathtt{pid}(t)$ 为进程类型，$t$ 为邮箱接口；send 对接收方接口做检查，receive 依据执行进程的接口约束收到的消息类型。2) 对每个函数推断其可被使用之邮箱类型的上下界（bounds），从而支持携带 $\mathtt{self()}$ 与 receive 的高阶函数在消息中流动。3) 程序员仅需为每个 spawn 出的进程标注接口，其余由 Elixir 现有子类型与约束求解机制推断。4) 对遗留代码，从 receive 分支对消息的使用方式得到接口上界，取最宽松解以恢复收到的 pid 与闭包类型。

Result: 系统可对在消息中传递、且引用 $\mathtt{self()}$ 和 receive 指令的高阶函数进行类型检查；仅需最少标注（每个进程的接口），其余全部推断；系统被证明是可靠的（sound）。对遗留代码，接口可由 receive 子句重构，所得最宽松解足以精确恢复接收到的 pid 与闭包的类型。

Conclusion: 该工作将 Elixir 的静态类型从函数式核心扩展到 actor 进程与消息传递层面，以邮箱接口加函数级上下界推断的方式，在低标注成本下实现了对高阶、跨进程代码的可靠类型化，并为无标注的遗留代码提供了基于 receive 子句的接口重构路径。

Abstract: We present a type system for the processes of Elixir, a dynamic language based on the actor model whose static type system covers only its functional core. Each process is typed by $\mathtt{pid}(t)$, where the ``interface'' $t$ is the type of the messages the process expects in its mailbox: sends are checked against the recipient's interface, and receives rely on the interface of the process that performs them.
  One of the difficulties of typing Elixir is that mailboxes are implicit: a function shipped in a message may evaluate $\mathtt{self()}$ and execute receive instructions, and both refer to whichever process eventually runs the function---$\mathtt{self()}$ returns that process's pid, receive reads that process's mailbox---so the mailbox they act on is not known where the function is written. We solve this problem by inferring, for every function, bounds on the type of the mailboxes it can be used with; as a result, the system types higher-order functions that travel in messages even when they contain reference to $\mathtt{self()}$ and receive instructions.
  The only new annotation the programmer writes is the interface of each spawned process; everything else is inferred by reusing the existing subtyping and constraint-resolution machinery of Elixir, and the system is proved sound.
  For legacy code, the interface can be reconstructed from the receive clauses: what the branches do with their messages bounds it from above, and the most permissive solution is sharp enough to recover received pids and closures.

</details>
