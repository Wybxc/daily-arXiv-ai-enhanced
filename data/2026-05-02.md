### [1] [Literate Execution](https://arxiv.org/abs/2604.26967)
*Joe Bond,Jacob Pake,Cristina David,Andrew McNutt,Trevor Sseguya Muwonge,Dominic Orchard,Roly Perera*

Main category: cs.PL

TL;DR: 本文提出"文字执行"(literate execution)概念，与Knuth的"文字编程"相反——不是将代码嵌入静态叙述，而是将文档和可视化视为可与运行程序一起计算的一等工件，并通过Fluid语言实现基于溯源追踪的运行时可探索解释。


<details>
  <summary>Details</summary>
Motivation: Knuth的文学编程将代码嵌入叙述中，但文档仍是静态的，无法与程序运行时动态交互，程序执行过程难以被探索和理解。

Method: 设计Fluid编程语言，其运行时具有溯源追踪(provenance-tracking)能力，记录输入与输出间的细粒度依赖关系，并将这些溯源关系呈现为交互式界面，让读者探索中间值如何贡献于最终结果。

Result: 通过Fluid语言实现了可视化、溯源与叙述的集成，使程序更可探索和自解释，同时使可探索的解释更易于编程。

Conclusion: 文字执行通过将文档和可视化作为一等运行时工件，结合溯源追踪，实现了动态可交互的程序理解方式，有望提升程序的可探索性和自解释性。

Abstract: \emph{Literate programming}, introduced by Knurth, interleaves code and prose so that a program can be read as both executable and explanatory text. We propose \emph{literate execution}, which inverts this relationship: rather than embedding code within a static narrative, we treat documentation -- and other expository elements such as visualisations -- as first-class artefacts that can be computed alongside a running program and then integrated into a view of its execution. We explore this idea through Fluid, a programming language with a provenance-tracking runtime that records fine-grained dependencies between inputs and outputs. These provenance relationships can be surfaced as interactions that allow readers to explore how intermediate values contribute to a result. By integrating visualisation, provenance, and exposition, literate execution aims to make programs more explorable and self-explanatory, and explorable explanations easier to program.

### [2] [A Monadic Implementation of Functional Logic Programs](https://arxiv.org/abs/2604.27863)
*Michael Hanus,Kai-Oliver Prott,Finn Teegen*

Main category: cs.PL

TL;DR: 本文提出将函数逻辑程序转换为单子表示，通过在非确定分支中实现记忆化（memoization），在Haskell等纯函数式环境中高效支持函数逻辑语言的特性（如函数模式、封装搜索），并通过静态和动态优化取得了优于当前Curry编译器的性能。


<details>
  <summary>Details</summary>
Motivation: 函数逻辑语言结合函数式与逻辑编程的优点，但其非确定性需求驱动策略可能导致未求值选择的重复计算，增加计算开销。虽在命令式语言中通过记忆化解决了该问题，但在Haskell等纯函数式环境中是否可行尚不明确。

Method: 将函数逻辑程序转换为单子表示，实现支持非确定性分支中记忆化的单子接口；同时集成函数模式（functional patterns）和封装搜索（encapsulated search）等高级特性；并分别采用静态和动态优化手段提升纯函数计算的性能。

Result: 该实现方法在性能上优于当前Curry语言的编译器，证明了在纯函数式环境中有效支持函数逻辑语言是可行的。

Conclusion: 通过单子表示和记忆化技术，可以在Haskell等纯函数式环境中高效实现函数逻辑语言的非确定性和需求驱动求值，且性能表现优异。

Abstract: Functional logic languages are a high-level approach to programming by combining the most important declarative features. They abstract from small-step operational details so that programmers can concentrate on the logical aspects of an application. This is supported by appropriate evaluation strategies. Demand-driven evaluation from functional programming is amalgamated with non-determinism from logic programming so that solutions or values are computed whenever they exist. This frees the programmer from considering the influence of an operational strategy on the success of a computation, but it is a challenge to the language implementer. A non-deterministic demand-driven strategy might duplicate unevaluated choices of an expression, which could duplicate the computational effort. In recent implementations, this problem has been tackled by adding a kind of memoization of non-deterministic choices to the expression under evaluation. Since this has been implemented in imperative target languages, it was unclear whether this could also be supported in a functional programming environment like Haskell. This paper presents a solution to this challenge by transforming functional logic programs into a monadic representation. Although this transformation is not new, we present an implementation of the monadic interface which supports memoization in non-deterministic branches. Additionally, we include more advanced features of functional logic languages, namely functional patterns and encapsulated search, in our approach. By optimizing our implementation for purely functional computations with both a static and dynamic approach, we are able to achieve a promising performance that outperforms current compilers for Curry.

</details>
