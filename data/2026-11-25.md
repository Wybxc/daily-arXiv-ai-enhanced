### [1] [SafeJIT: A Speculating JIT Engine Verified Down to the Machine Code](https://arxiv.org/abs/2611.28436)
*Gabriel Ebner*

Main category: cs.PL

TL;DR: SafeJIT 是一个带推测式基线 JIT 的小型 JavaScript 引擎，作者在 Lean 4 中给出机器验证证明：其静态链接的 RISC-V 与 x86-64 可执行文件在 Linux 用户进程模型下对任意输入都不会崩溃（stuck），证明对象为最终二进制本身，在 Sail ISA 模型上逐指令执行，覆盖解析器、字节码编译器、解释器、JIT 编译器及其可生成的全部机器码、GC、运行时与 freestanding libc，且不信任 C 编译器、汇编器、链接器与浮点运算。


<details>
  <summary>Details</summary>
Motivation: JIT 编译器是现代软件中受攻击最严重的一类组件：它编译由攻击者挑选的程序、基于受攻击者影响的类型反馈做推测，并以完全的原生权限执行生成代码。一个被错误消除的守卫或缺失的去优化即可导致内存破坏。因此需要把安全性论证从“源码层”推进到“真正运行的二进制层”，且不能信任编译工具链与浮点语义。

Method: 构建小型 JS 引擎 SafeJIT（含推测式基线 JIT），在 Lean 4 中用基于 iris-lean 的分离逻辑，针对一个 Linux 用户进程模型做机器验证。其 stuck 状态被精确定义为进程可崩溃的全部方式（包括取指于尚未设为可执行或指令缓存未刷新的代码）。证明以 Sail ISA 模型（RISC-V 采用官方模型）逐指令执行实际发布的 RISC-V 与 x86-64 静态链接可执行文件，范围覆盖解析器与字节码编译器、解释器及其类型反馈记录、JIT 编译器、JIT 对任意程序与任意反馈可生成的全部机器码（类型守卫、守卫消除、循环类型事实、带去优化元数据的寄存器分配、内联缓存、去优化与栈上替换）、标记-清扫 GC、运行时以及 freestanding libc；C 编译器、汇编器、链接器与浮点运算均不纳入可信基。

Result: 得到一条关于最终发布二进制的定理：在 Linux 用户进程模型下，这些二进制在逐指令执行的 Sail ISA 语义上对任何输入都不会进入 stuck 状态，即不会崩溃。证明覆盖二进制中的全部代码路径，并以分离逻辑处理程序与进程状态，从而把 JIT 生成代码的正确性与去优化机制一并纳入验证范围。

Conclusion: 该工作展示了端到端、跨越工具链与浮点语义、并以真实二进制与 ISA 模型为验证对象的 JIT 引擎安全性证明是可行的，将 JIT 安全保证从源码级推测与守卫正确性提升到“发布二进制绝不崩溃”的机器验证保证，为高保障 JIT 的设计与验证提供了可复用的方法论与可信基。

Abstract: JIT compilers are among the most attacked components of modern software. They compile attacker-chosen programs, speculate on attacker-influenced type feedback, and run the result at full native privilege. A single wrongly eliminated guard or a missing deoptimization becomes memory corruption. We present SafeJIT, a small JavaScript engine with a speculating baseline JIT, together with a machine-checked proof in Lean 4 that its statically linked RISC-V and x86-64 executables never crash, on any input, in a model of a Linux user process. The theorem is about the shipped binaries, executed instruction by instruction on Sail ISA models (for RISC-V, the official one), and it covers everything in them: the parser and bytecode compiler, the interpreter and its type-feedback recording, the JIT compiler, all machine code the JIT can generate for any program and any feedback (type guards, guard elimination, loop type facts, register allocation with deoptimization metadata, inline caches, deoptimization and on-stack replacement), a mark-sweep garbage collector, the runtime, and a freestanding libc. The C compiler, assembler and linker are not trusted, and neither is floating-point arithmetic. The proof uses separation logic (iris-lean) over a model of a Linux user process whose stuck states are exactly the ways a process can crash, including fetching code that has not been made executable or whose instruction cache has not been flushed.

### [2] [VAPY: Circuit Optimization with Backpropagation](https://arxiv.org/abs/2611.28554)
*Anthony Yang,Ron Dubinsky,Yu-Neng Wang,Sara Achour*

Main category: cs.PL

TL;DR: VAPY 是一个 Verilog-A 到 JAX 的转译器，将 PDK 中的器件模型编译为可自动微分的 JAX 代码，从而在 Circulax 电路仿真器中实现高效的梯度优化。


<details>
  <summary>Details</summary>
Motivation: 模拟电路的设计参数灵敏度支持基于梯度的优化，但 PDK 中基于 Verilog-A（数千行代码）的器件模型难以求得精确灵敏度。有限差分法每个梯度需 N+1 到 2N 次仿真，参数多时代价过高。

Method: VAPY 通过污点分析（taint analysis）仅重写必要的控制流为 JAX 兼容调用以降低开销，将 Verilog-A 器件模型转译为可自动微分的 JAX 代码，并与基于 JAX 的 Circulax 电路仿真器配合使用，在 SkyWater SKY130 PDK（基于 BSIM4 模型）上优化三个模拟电路。

Result: VAPY 生成的模型梯度与有限差分梯度高度吻合；在电路求解次数减少 40 倍以上的情况下达到相当的设计质量，且相比贝叶斯优化损耗降低最多 40%。

Conclusion: VAPY 有效解决了 PDK Verilog-A 模型的精确梯度计算难题，实现高效、低成本的梯度优化，显著优于有限差分与贝叶斯优化。

Abstract: Parameter sensitivities of analog circuits enable the use of gradient-based design optimization methods and unlock a range of sensitivity analyses. However, it remains a challenge to compute exact design parameter sensitivities for circuits that use PDKs, which use Verilog-A device models comprised of thousands of lines of code. Finite difference methods, which estimate gradients through simulation, require N + 1 to 2N simulations for each gradient depending on the method, which can become prohibitively expensive when many parameters are optimized. We present VAPY, a Verilog-A to JAX transpiler that compiles Verilog-A device models into autodifferentiable JAX code, enabling optimization with Circulax, a JAX-based circuit simulator. VAPY employs taint analysis to ensure only the necessary control-flow is rewritten with JAX-compatible calls, reducing control-flow overheads. We use VAPY and Circulax to optimize three analog circuits implemented in the SkyWater SKY130 PDK, which is built on the BSIM4 device model. VAPY-generated model gradients closely match finite-difference gradients, achieving comparable design quality in over 40X fewer circuit solves and up to 40% lower loss than Bayesian optimization.

### [3] [An End-to-End Theory for Compositional Symbolic Execution: From Expressive Specifications to SMT (Extended Version)](https://arxiv.org/abs/2611.28916)
*Shivanandan Tamil Kumaran,Andreas Lööw,Philippa Gardner*

Main category: cs.PL

TL;DR: 本文在Rocq中构建了面向组合符号执行(CSE)的端到端、更贴近真实工具的机械化理论：前端支持代数数据类型、逻辑函数与引理，后端通过可复用的SMT-LIB机械化与经证明正确的编码连接到SMT求解器。


<details>
  <summary>Details</summary>
Motivation: 现有CSE形式化理论中的理想化模型与真实工具之间存在明显鸿沟，缺乏既能刻画实用验证模式、又可与真实SMT求解器对接的基础理论。

Method: 在Rocq证明助手中机械化CSE理论；构建独立的可复用SMT-LIB标准形式化；给出从CSE后端查询到SMT-LIB查询的编码并证明其正确性，处理语义差异并利用类型信息进行优化；抽取经验证的编码，在Gillian的大部分求解器查询上与工具自带编码并行实证评估。

Result: (1) 捕获实用验证模式的CSE理论；(2) 可独立复用的SMT-LIB Rocq机械化；(3) 经证明正确、考虑语义差异并基于类型信息优化的后端编码；(4) 在Gillian多数求解器查询上的实证评测证据。

Conclusion: 该工作推进了CSE形式化在“前端表达力”与“后端求解器连接”两端的真实性，为CSE工具提供可验证的基础理论支撑。

Abstract: Compositional symbolic execution (CSE) is a powerful technique for program verification and bug-finding, yet existing formal theories of CSE do not sufficiently bridge the gap between idealised models and real-world tools. We present progress towards a foundational, realistic, end-to-end theory of CSE in the Rocq proof assistant. Our theory advances realism at both ends of the CSE pipeline: it supports an expressive frontend with algebraic data types, logical functions, and lemmas; it also provides a verified connection to SMT-LIB compliant SMT solvers. Our contributions include: (1) a CSE theory that captures practical verification patterns; (2) a standalone, reusable Rocq mechanisation of the SMT-LIB standard; (3) a proven-correct encoding from CSE backend queries to SMT-LIB queries that accounts for semantic discrepancies and optimises using type information; and (4) empirical evidence for the backend by extracting our verified SMT-LIB encoding and running it alongside the CSE tool Gillian's own encoding on a majority of its solver queries.

### [4] [Cache the Knowledge, Not Just the Prompt: Dynamic Datalog as the Action Language for LLM Agents](https://arxiv.org/abs/2611.29709)
*Bruno Rucy Carneiro Alves de Lima,Victor Henrique Cabral Pinheiro*

Main category: cs.PL

TL;DR: 提出将 Datalog REPL（基于动态 Datalog 引擎的会话）作为 LLM 智能体访问知识图谱的工具，使会话内共享的规则与推导事实被复用，从而在准确率不降的前提下减少输出 token 与延迟。


<details>
  <summary>Details</summary>
Motivation: 现有智能体对每个问题单独生成程序，且工具从零开始评估，会话内共享的逻辑与求值结果无法复用；用 SQL 建表或 Python 命名空间缓存又难以兼顾“读取像表一样快”和“数据变化后像视图一样保持最新”。

Method: 为智能体提供 Datalog REPL：一个运行于动态 Datalog 引擎之上的会话，规则可像事实一样插入与撤回，且推导事实保持最新；配合提示缓存复用模型对会话共有部分的处理，Datalog REPL 则复用其求值结果。在三个知识图谱上以问题链形式，与 SQL 智能体和 Python 智能体进行对比，涉及两个模型。

Result: 在 180 个案例中的 179 个，REPL 保留的关系被后续问题复用；输出 token 更少，SQL 与 Python 智能体多写 23%–82%。使用 SQL 表或 Python 命名空间时，Claude Haiku 5.5 几乎不为后续问题存储任何内容；1300 万事实下 7 问链条的中位耗时为 48 s 与 56 s，而 REPL 为 31 s。Claude Opus 5.5 通过把表存入 SQL 达到 REPL 水平，但数据变化时只能存视图，每次读取都需重新求值。

Conclusion: REPL 保留的关系兼具“表式读取”与“视图式实时性”的优点。尽管 Datalog 相对 SQL 和 Python 是小众语言，但开启思考模式时模型使用它的作答准确率与二者相当。

Abstract: An LLM agent that answers questions about a knowledge graph writes a program per question, and its tools evaluate each from scratch. We give the agent a Datalog REPL, a session over a dynamic Datalog engine, in which rules are inserted and retracted like facts while derived facts stay current. Prompt caching reuses the model's processing of what a session shares, and the Datalog REPL reuses the evaluation of it. On chains of questions over three knowledge graphs, agents reuse a relation that the REPL keeps in 179 of 180 cases, with two models, and write fewer output tokens: SQL and Python agents write 23 to 82% more. With SQL tables or a Python namespace, Claude Haiku 5.5 stores almost nothing for later questions, and a chain of seven questions at 13 million facts takes it a median of 48 and 56 s, against 31 s with the REPL. Claude Opus 5.5 matches the REPL by storing tables in SQL, and when the data changes it stores views, which are evaluated again at every read. A relation that the REPL keeps is read like a table and stays current like a view. Datalog is a niche language beside SQL and Python, and with thinking enabled the models answer as accurately with it.

</details>


### [5] [What Field Enumeration Costs to Compile in C++26: Native Reflection, Structured-Binding Packs, Reflection Libraries and Hand-Written Serializers on GCC 16](https://arxiv.org/abs/2611.30250)
*Denys Kachalenko*

Main category: cs.PL

TL;DR: 该论文在 GCC 16.2.0 上对比 C++26 静态反射、结构化绑定包、手写代码、X-macros 与库（Boost.PFR、reflect-cpp、Glaze）在结构体序列化中的编译期与 -O2 开销，并做随机交错的单因子对照。


<details>
  <summary>Details</summary>
Motivation: C++26 引入多种枚举结构体字段的标准机制（P2996+P3394、P1061），同时存在手写代码、X-macros 和已支持 C++26 路径的库；缺少在统一序列化基准下对各类机制开销的系统、可比测量。

Method: 使用输出字节完全一致的序列化器，在 GCC 16.2.0 上前端与 -O2 分别计时；采用随机交错轮次，并对每个单因子对照做代码级校验；涉及 16 个标量字段的结构体、异质类型图、200 个结构体的整体 TU，以及 16/128 字段规模，另含 -freflection 开关对照。

Result: 前端阶段，P2996 示例形式的 define_static_array span 展开语句约等于 Boost.PFR，是 P1061 pack 的 7.96 倍，而 P1061 接近手写代码；常量数组循环为其 0.47 倍，约一半开销来自 span。与 P1061 的比值在异质类型图和 -O2 下缩小。整 TU 前端：200 结构体下内联原生枚举 0.59 s、Boost.PFR 0.56 s、reflect-cpp 与 Glaze 的 C++26 路径 3.86–4.13 s（其 visitor 还计算字段名）。16 字段时各库 C++26 路径优于其 pre-C++26 路径，但 Glaze 在 128 字段时反转（v9.1.0）；Boost.PFR C++17 路径随类型数近二次增长；同名单重载手写序列化器随类型数超线性增长。仅 -freflection 即令无反代码每类型开销升至 1.264 倍（16.2.0）、2.578 倍（16.1.0）。span 形式部分开销随结构体数增长，归因于 GCC 以二次时间注册块作用域静态变量（GCC PR128928）。

Conclusion: 机制选择应结合点版本与规模：前端主要成本由库而非机制决定，P1061 最接近手写；span 形式存在可消除的额外开销与 GCC 缺陷；-freflection 本身带来显著开销且随点版本变化，故跨 GCC 版本比较机制需谨慎。

Abstract: C++26 adds standard ways to enumerate a struct's fields, among them static reflection (P2996, with P3394 annotations) and structured-binding packs (P1061), alongside hand-written code, X-macros and libraries (Boost.PFR, reflect-cpp, Glaze) that now ship pre-C++26 and C++26 paths. We time each in a struct serializer with byte-identical output on GCC 16.2.0, at the front end and at -O2, in randomized interleaved rounds with code-level checks of every single-factor contrast. At the front end, inline native enumeration in the form used in several of P2996's own examples, an expansion statement over the std::span of define_static_array, costs about as much per struct of 16 scalar fields as Boost.PFR and 7.96x a P1061 pack, itself about as cheap as hand-written code. The same loop over a constant array costs 0.47x as much: about half of the span form's cost comes with the span. The ratio to P1061 shrinks on a heterogeneous type graph and at -O2. In a whole translation unit at the front end the library outweighs the mechanism: 200 structs take 0.59 s with inline native enumeration, 0.56 s with Boost.PFR and 3.86-4.13 s with the C++26 paths of reflect-cpp and Glaze, whose visitors also compute field names. Per type, each library's C++26 path is cheaper than its pre-C++26 path at 16 fields, but Glaze's gain reverses at 128 fields (pinned release v9.1.0); Boost.PFR's C++17 path grows almost quadratically with the number of types. Hand-written serializers sharing one overloaded name grow superlinearly with the number of types. The -freflection flag alone makes reflection-free code up to 1.264x costlier per type on GCC 16.2.0 and up to 2.578x on 16.1.0, so comparisons between mechanisms depend on the point release. Part of the span form's cost grows with the number of structs, which we trace to GCC registering block-scope statics in quadratic time (reported as GCC PR128928).

### [6] [Ziv: A Language for Correctly Rounded Math Libraries](https://arxiv.org/abs/2611.30346)
*Lucas Yunkyu Lee,Sungjin Hwang,Wonyeol Lee*

Main category: cs.PL

TL;DR: 提出Ziv编程系统（小语言+标准库+可证明可靠的C编译器），通过扩展精度抽象与分阶段编译期求值，将预计算与运行时计算统一于一个程序，实现可正确舍入的数学库，重写19个函数代码量减少2.63倍且性能相当。


<details>
  <summary>Details</summary>
Motivation: 正确舍入的数学库难以开发：现有实现语言缺乏扩展精度算术的高层抽象，也缺乏将预计算与运行时计算结合的分阶段计算支持，导致实现难以抽象、常量硬编码在用独立程序预计算的代码中，使库难以编写、理解和修改。

Method: Ziv系统由三部分组成：小语言、丰富的标准库、面向C的可证明可靠的编译器；提供扩展精度数的类型与运算等高层数值抽象；支持对输入无关表达式进行编译期求值的分阶段计算；嵌入Julia中使用。

Result: 重实现两个最先进正确舍入库中的19个函数，代码行数减少2.63倍，性能具有竞争力；另实现3个新函数并自动探索824,256种变体，相比任意精度库平均加速96.5倍。

Conclusion: 高层数值抽象与分阶段计算的结合能在保持性能的同时显著提升正确舍入数学库的可写性、可理解性与可修改性，并支持自动化设计空间探索。

Abstract: Developing performant, correctly rounded math libraries is challenging. Such implementations often rely on extended-precision arithmetic for correct rounding and precomputed constants for performance. Existing implementation languages, however, provide limited support for (i) high-level abstractions for such arithmetic and (ii) staged computation to combine precomputation and runtime computation in one program. As a result, existing implementations often miss abstraction opportunities and hard-code constants precomputed using separate programs. These practices make it difficult to write, understand, and modify these libraries.
  We present Ziv, a programming system for developing correctly rounded math libraries. It consists of a small language, a rich standard library, and a provably sound compiler targeting C. Ziv supports (i) high-level numerical abstractions via types and operations for extended-precision numbers, and (ii) staged computation via compile-time evaluation of expressions known to be input-independent. These features enable high-level code that unifies precomputation and runtime computation. We embed Ziv in Julia and evaluate it by reimplementing 19 functions from two state-of-the-art libraries targeting correct rounding; we achieve competitive performance with 2.63$\times$ reductions in lines of code. We also implement three new functions and automatically explore 824,256 variants, achieving 96.5$\times$ average speedup over an arbitrary-precision library.

</details>
