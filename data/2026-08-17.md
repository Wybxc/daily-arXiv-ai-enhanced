### [1] [A Barrier-Free Synchronization Algorithm for Multi-Engine AI Accelerators](https://arxiv.org/abs/2608.13757)
*Chungha Sung,Nikil V. Shyamsunder,Hanliang Zhang,Daniel Kroening,Joonwon Choi*

Main category: cs.PL

TL;DR: 本文提出了一种面向多引擎AI加速器（如AWS Trainium）的无屏障同步算法，通过运行时动态计算阈值来精确满足跨嵌套动态循环的数据依赖，替代传统的循环边界全引擎屏障，在Neuron ISA编译器后端实现后，ML内核延迟降低10-45%，同步受限微基准测试加速3.3倍，并在Lean证明助手中通过双模拟验证了算法满足最小同步正确性准则。


<details>
  <summary>Details</summary>
Motivation: 多引擎AI加速器（如AWS Trainium）由多个专用计算引擎并行执行，编译器需同步引擎间的数据依赖。直线代码可通过静态计算指令完成阈值来同步，但循环不存在静态阈值；简单方案是在循环边界插入全引擎屏障以重置同步状态，但这牺牲了并行度。作者旨在消除这种屏障开销，实现精确的循环内依赖同步。

Method: 提出一种无屏障同步算法：核心思想是在运行时从跟踪的循环迭代次数动态计算依赖的阈值，从而在具有任意嵌套、动态有界循环的结构化控制流中精确地强制执行每个数据依赖。算法作为编译器后端pass在AWS Neuron ISA层面实现；正确性方面，形式上刻画了正确性所需的最小同步量，并在Lean证明助手中通过双模拟（bisimulation）验证算法满足该准则。

Result: 在ML内核测试集上，相比基于屏障的基线方案延迟降低10-45%；在同步受限的微基准测试上获得3.3倍加速；在多种场景下达到或超过手工调优的分配方案。

Conclusion: 动态阈值同步是替代全引擎屏障的有效方案，能在保证正确性（经形式化验证）的同时显著提升并行度和性能，为多引擎AI加速器的编译器同步优化提供了新的思路与验证框架。

Abstract: Multi-engine AI accelerators such as AWS Trainium comprise specialized compute engines that execute in parallel, and the compiler must synchronize the data dependencies between them. For straight-line code this is simple: each dependency reduces to waiting for a threshold count of instruction completions, which the compiler computes statically. Loops admit no such static threshold; a simple solution inserts all-engine barriers at iteration boundaries, resetting synchronization state so each loop body can be treated as straight-line, at the cost of parallelism.
  We present a barrier-free synchronization algorithm that instead enforces each dependency precisely across structured control flow with arbitrarily nested, dynamically bounded loops. The key idea is to compute dynamic thresholds at runtime from tracked loop iteration counts.
  We implemented it as a compiler backend pass at the AWS Neuron ISA level. On a suite of ML kernels, it reduces latency 10-45% relative to the barrier-based baseline, achieves a 3.3x speedup on a synchronization-bound microbenchmark, and often matches or exceeds hand-tuned manual allocation.
  Issuing a consumer too early violates its dependency, while issuing too late unnecessarily stalls execution. We formally characterize the minimum synchronization required for correctness and verify in the Lean proof assistant, via bisimulation, that our algorithm meets this criterion.

### [2] [GPU Offload in Rust: Portable, Safe, and Fast](https://arxiv.org/abs/2608.13759)
*Manuel S. Drehwald,Marcelo Domínguez,Kevin Sala,Alán Aspuru-Guzik,Johannes Doerfert*

Main category: cs.PL

TL;DR: 本文提出了一个内置于Rust编译器(rustc)和LLVM后端的多厂商GPU编译框架，在不牺牲内存安全的前提下实现零开销的GPU编程。通过利用Rust的类型系统、所有权系统和严格别名保证(noalias)来优化数据传输，解决跨厂商ABI降低不匹配问题，并引入两遍编译流水线。在RAJAPerf基准测试中，生成的LLVM IR在GPU内核性能上与原生手写优化的CUDA和HIP C++基线相当。


<details>
  <summary>Details</summary>
Motivation: 高性能GPU编程传统上需要在执行效率和内存安全之间进行权衡。Rust虽然在主机CPU上通过严格的所有权模型保证了编译期内存安全，但将其应用于大规模并行GPU执行环境时，要么受限于厂商绑定的DSL，要么需要退回到显式的unsafe原始指针操作。作者希望打破这一困境，实现既安全又高效的GPU编程体验。

Method: 该方法构建了一个多厂商GPU编译框架，原生集成在rustc和LLVM后端中。核心方案包括：(1) 利用Rust的类型系统、所有权系统和noalias严格别名保证来高效管理和优化数据转移；(2) 通过LLVM的Offload基础设施实现数据传输优化；(3) 针对主机与设备目标之间跨厂商ABI降低不匹配问题，引入了一种两遍编译流水线，能够安全处理手动和编译器生成的内存移动。

Result: 在RAJAPerf基准测试集上进行评估，该rustc方案能够生成具有竞争力的LLVM IR用于GPU内核，在GPU内核性能上达到了与原生、手写优化的CUDA和HIP C++基线相当的水平。

Conclusion: 该研究证明了通过Rust编译器原生的多厂商GPU编译框架，可以在保持编译期内存安全的同时实现与手写原生CUDA/HIP C++相当的GPU内核性能，消除了传统上安全性与效率不可兼得的取舍。

Abstract: High-performance GPU programming has traditionally forced a compromise between execution efficiency and memory safety. While Rust guarantees compile-time memory safety for host CPUs via its strict ownership model, applying these constraints to massively parallel GPU execution environments has previously mandated either vendor-locked Domain-Specific Languages (DSLs) or escaping to explicit unsafe raw pointers. This paper presents a zero-overhead, multi-vendor GPU compilation framework built natively into the Rust compiler (rustc) and LLVM backends.
  We leverage Rust's rich type system, ownership system, and strict aliasing guarantees (noalias) to efficiently manage and optimize data transfers through LLVM's Offload infrastructure. We expose the technical challenges of cross-vendor ABI lowering mismatches between Host and Device targets and introduce a two-pass compilation pipeline capable of safely handling both manual and compiler-generated memory movements. Evaluating our framework on RAJAPerf demonstrates that our rustc-based solution can generate competitive LLVM IR for GPU kernels, achieving a solid kernel performance against native, hand-optimized CUDA and HIP C++ baselines.

</details>


### [3] [Memory Allocation for Constant-Bounded Programs](https://arxiv.org/abs/2608.14471)
*Vinícius Silva,Kael Soares,Márcio Costa e Fernando Magno Quintão Pereira*

Main category: cs.PL

TL;DR: 本文研究了常数有界程序（执行长度对所有输入在语法上受限的程序）的内存分配问题，通过将控制流视为树结构并采用树扫描分配策略结合内存碎片整理，实现了最优栈空间使用的多项式时间近似。在Elixir-to-eBPF编译器和MLIR程序静态堆分配器中部署，实际eBPF工作负载栈空间减少超90%。


<details>
  <summary>Details</summary>
Motivation: 常数有界程序（如经过验证的内核扩展、加密例程和固定形状机器学习模型）具有执行长度受语法约束的特性，这使得精确的栈空间优化成为可能。传统内存分配策略在栈空间利用率上存在显著浪费，需要一种利用常数有界特性实现紧致、多项式时间可计算的分配方案。

Method: 将控制流视为树结构，应用树扫描分配策略，并引入内存碎片整理机制。该方法保证内存使用限制为最大活动内存加上最大缓冲区大小，且在允许就地交换时达到最优。在Elixir-to-eBPF编译器中作为栈空间spiller使用，并在MLIR Structured Control-Flow方言中用作静态堆分配器。

Result: 在真实eBPF工作负载上栈空间减少超过90%；即便在激进的代码扩展下，碎片整理很少被触发，内存使用仅为朴素分配策略所需内存的一小部分。

Conclusion: 常数有界性能够实现紧致且高效的内存分配，所提出的树扫描加碎片整理方法在理论和实践上均表现优越，适用于eBPF和MLIR等多种场景。

Abstract: This work studies memory allocation for constant-bounded programs, whose execution length is syntactically limited for all inputs. Examples of such programs include verified kernel extensions, cryptographic routines, and fixed-shape machine-learning models. We show that constant boundedness enables a tight, polynomial-time approximation of optimal stack usage by viewing control flow as a tree and applying a tree-scan allocation strategy augmented with memory defragmentation. Our approach guarantees memory usage bounded by the maximum live memory plus, at most, the size of the largest buffer, and is optimal when in-place swapping is permitted. We deploy the proposed allocator in two scenarios. First, in an Elixir-to-eBPF compiler, as a spiller that optimizes stack space. Second, as a static heap allocator for bounded MLIR programs using the Structured Control-Flow dialect. Results demonstrate stack reductions exceeding 90% on real eBPF workloads and show that, even under aggressive code expansion, defragmentation is rarely required and memory usage remains a small fraction of that required by naive allocation strategies.

</details>
